# ADR 0002: API clients, MCP agents, mobile and AI

- Status: Accepted
- Date: 2026-11-01
- Deciders: TechDufus

## Context

ADR 0001 and its design describe a dash that a browser uses. A review of that plan against the code ([../design/clients-and-ai.md](../design/clients-and-ai.md), section K) found that it has no machine-client authentication, that authorisation is role-only, that the proxy role mapping fails open, and that the settings API has secret-exfiltration paths. The same review asked for two new kinds of client: a native Android app, and AI agents that manage the infrastructure over MCP with the user's permissions. It also asked how AI should be integrated without handing an agent unreviewed write access.

This ADR records the outcomes of that design, section S, which continues the decisions of section J of [../design/plugins-and-config.md](../design/plugins-and-config.md) and ADR 0001. The design merged on 2026-11-01 (dash PRs #1 and #5). The 17 decisions are numbered S.1 to S.17 as in the design, and each cites the design section that holds the detail.

Decision status:
- **Decided by the owner on 2026-10-31:** S.4, S.5, S.8, S.10, S.11, S.12 and S.13.
- **Accepted with the design (merged 2026-11-01):** S.1 to S.3, S.6, S.7, S.9 and S.14 to S.17.

S.14 amends decision 4 of ADR 0001. ADR 0001 is not edited; where the two differ, this ADR wins for the points named in S.14. Decision 12 of ADR 0001 (two roles) stays; S.3 narrows it with scopes.

## Decisions

### S.1 Versioned API, OpenAPI, error codes and request IDs

**Decision.** The public API lives under `/api/v1` and the SPA uses it too, so there is one contract and no private routes. Unversioned core paths return 404 once moved, with no aliases. The API is stable from 1.0; breaking changes in 0.x are called out in release notes (ADR 0001 decision 19). Every error body is `{"error", "code", "requestId", "details?"}` with `ErrCode*` constants in `internal/model`, and every response carries an `X-Request-Id` header that appears in logs and audit records. OpenAPI 3.1 is generated by `dash api openapi` into `docs/api/openapi.json`, and drift fails `make check`. Every object in a plugin payload carries a `ref` (`<plugin>:<Kind>/<id>`). `GET /api/v1/me` reports the server's capabilities and the caller's scopes. CORS headers are off by default and apply to bearer clients only, from an explicit origin list. (Design L.1 to L.8.) Proposed with the design; accepted.

**Alternatives considered.**
- Keep the unversioned `/api` and add `/api/v1` only for new endpoints: leaves two contracts, one of them private to the SPA, and a native app would build against routes that may change.
- Keep unversioned paths as aliases during a transition: dash has one deployment and no external clients yet, so aliases would be dead weight.
- A hand-maintained OpenAPI file: drifts from the code. A route that cannot be registered without a spec entry cannot be undocumented.
- A wildcard CORS policy: a permissive default would expose the API to any web page. CORS is never `*`, never sent with credentials, and only for bearer requests.

**Consequences.** Moving the core routes is a breaking change in 0.x (P2.10). The router needs typed registration helpers, and the P2.2 schema reflector becomes part of the build. Clients can read the spec and the `ref` grammar without knowing a plugin's URL scheme. The stream and request limits first added as constants by the hardening PR become `server.limits.*` settings in P2.11.

### S.2 One principal per request

**Decision.** Every request resolves to exactly one principal, in this order: a bearer token (proxy headers are ignored; a session cookie sent as well gives 400 `ambiguous_credentials`), the session cookie, proxy headers from trusted TCP peers, the anonymous viewer if enabled, otherwise 401 with `WWW-Authenticate` pointing at the protected resource metadata. CSRF and Origin checks apply to non-bearer requests only. The SPA never uses bearer tokens. An "interactive principal" is a person in the browser (kinds `session`, `proxy`, `dev`, `demo`). (Design M.1, M.2.) Proposed with the design; accepted.

**Alternatives considered.**
- Merge credentials, for example bearer plus proxy headers: lets a proxy-supplied identity and a token disagree, and lets a client that skips the proxy influence who it is.
- Apply CSRF checks to bearer requests too: a bearer token is not attached by the browser, so there is nothing for a forged request to ride on, and the check would only block non-browser writes.

**Consequences.** `auth.Principal` replaces `auth.User` in the action and middleware code (P4.2, P7.1). Bearer clients can skip an identity-aware proxy safely, because a bearer request cannot forge a user with headers (see S.5 for the deployment consequence). Ambiguous requests fail loudly instead of picking a credential.

### S.3 Roles stay; scopes and audiences narrow them

**Decision.** The two roles of ADR 0001 decision 12 stay. Scopes narrow the role ceiling: `read`, `logs`, `actions:<plugin>`, `approvals` and `push`. Effective permission is role ∩ scopes ∩ feature switches. Each token is bound to one audience, `api` or `mcp`, and a token used at the other surface gets 401 `invalid_token`. Settings, token and OAuth-client management and audit reads are interactive-only; a bearer principal gets 403. The `approvals` and `push` scopes can be held only by the built-in first-party app (S.5), never by a PAT or static token. (Design M.3, M.4, M.6.) Proposed with the design; accepted.

**Alternatives considered.**
- Role-only authorisation for tokens: a token would carry the full power of its user, so an agent that only needs to read would also be able to run actions.
- A third `operator` role: still rejected for v1 (ADR 0001 decision 12); scopes give the needed granularity for machine clients without changing the human role model.
- A single audience for all tokens: an MCP token an agent holds could then be replayed against the full REST API (confused deputy; see the MCP security considerations cited in the design).

**Consequences.** Every route needs a declared scope, which the OpenAPI helpers (S.1) record. Consent and token screens must explain scopes. Because `approvals` is limited to the first-party app, an agent can never approve its own MCP actions (S.10).

### S.4 Personal access tokens and static tokens

**Decision. Decided by the owner on 2026-10-31.** Personal access tokens (PATs) have the form `dash_pat_<id>_<secret>`, are shown once, are stored as SHA-256 and are compared in constant time. Expiry is required: default 30 days, maximum 365. Allowed scopes are `read`, `logs` and `actions:<id>` (admin only), with an optional `actionNamespaces` list. Revocation is immediate. A token's role is derived on every request from the current mapping applied to the creator's recorded groups and role-claim value. Static tokens for GitOps installs are listed in `auth.tokens` by hash only; a static `mcp` token cannot hold `actions:*`, because approvals need an owning user. 300 requests per minute per `api` token. (Design M.5.)

**Alternatives considered.**
- Tokens that never expire: a forgotten token stays valid forever. A mandatory expiry makes rotation the default.
- Storing tokens in plaintext or reversibly encrypted: a leaked `credentials.yaml` would then leak working credentials. Only the hash is kept.
- Static tokens as plaintext in config: config is often in git. Only the hash goes into config, and `dash token generate` prints both.
- OAuth only, with no PATs: headless scripts and CI would need an interactive flow. RFC 8628 device grant was also rejected (S.17), since PATs cover headless use.

**Consequences.** PATs and grants follow the identity provider only when the user is seen interactively, so offboarding a user at the provider does not reach their tokens until an admin revokes them in dash; this is documented. Tokens never carry secrets in logs: `dash_pat_` is in the redaction patterns (design C.6). `credentials.yaml` (S.6) is a dependency. Delivered in P7.1.

### S.5 Built-in OAuth 2.1 authorisation server

**Decision. Decided by the owner on 2026-10-31.** In `local`, `oidc` and `proxy` modes dash is its own OAuth 2.1 authorisation server, so MCP clients and the Android app get tokens without an external provider. It is disabled in `none` mode and when there is no writable data dir. Specifics:
- PKCE S256 only; `resource` (RFC 8707) selects the audience; the authorisation response carries `iss` (RFC 9207); metadata follows RFC 8414 and RFC 9728; revocation follows RFC 7009.
- Clients are the built-in `dash-android` (public, `api` audience, the only client that can receive `approvals` and `push`), Client ID Metadata Documents (https only, global addresses unless allowed, 5 s timeout, 64 KiB cap, no redirects, cached 24 h) and clients listed in `auth.oauth.clients`.
- No Dynamic Client Registration.
- Authorisation codes last 60 s and are single use. Access tokens last 15 minutes and are sealed (XChaCha20-Poly1305) so they can be validated without a database row. Refresh tokens are rotated on every use; reuse revokes the grant; idle expiry is 30 days and absolute expiry 180 days.
- The consent screen pre-ticks only `read`, and its wording for `actions:*` depends on the audience.
- In `proxy` mode, only `/oauth/authorize` goes through the identity-aware proxy; the token, revoke, discovery, `/mcp` and bearer API paths reach dash directly, with dash trusting only the proxy's own address. The chart gains `routes.direct` for this.

(Design M.6, M.10.)

**Alternatives considered.**
- Delegate to the external identity provider only: ties MCP and mobile to one provider, and `local` and `proxy` modes have none to delegate to.
- Dynamic Client Registration: deprecated in MCP 2026-07-28 and an open registration endpoint is an abuse surface. CIMD and pre-registered clients replace it.
- PKCE `plain` or clients without PKCE: weaker, and not part of OAuth 2.1.
- RFC 8628 device grant: PATs cover headless use and capable phones use RFC 8252 (S.17).
- Opaque access tokens looked up in a database: needs write load on every refresh and a database (S.6). Sealed tokens are validated by decrypting and re-checking the grant.

**Consequences.** A new package with real security surface: it needs strict redirect matching, rate limits, and tests for PKCE downgrade, refresh reuse and CIMD server-side request forgery (private addresses refused). Without `DASH_SECRET_KEY`, access tokens use a per-process key, so a restart invalidates them and clients refresh. Behind an identity-aware proxy the operator must route the direct paths around it. Delivered in P7.2.

### S.6 `credentials.yaml` with no backups; still no database

**Decision.** Credential state (PATs, OAuth grants, push subscriptions, per-user session epochs and the VAPID key pair) lives in `$DASH_DATA_DIR/credentials.yaml`, mode 0600, with `schemaVersion`, the same atomic write as the settings store, the store's writer mutex and `.lock`, and **no `.bak` rotation**, so a restore can never bring back a revoked credential. The VAPID private key is `enc:v1`-encrypted. There is no database; this matches ADR 0001 decision 3. Revisit only past one sustained write per second. (Design M.7.) Proposed with the design; accepted.

**Alternatives considered.**
- Put credentials in `ui-settings.yaml`: that file rotates five backups, so a revoked token could be restored from one.
- SQLite now: the deferred option of ADR 0001 decision 3. Writes are rare (token changes, one refresh per client per 15 minutes, `lastUsedAt` flushes), so the extra dependency and the loss of a readable, diffable file are not justified.
- Keep credentials in memory only: every restart would revoke every token and grant.

**Consequences.** Backups of `credentials.yaml` must be handled by the operator's own backup tooling; a restore from an older copy can bring back credentials that were later revoked, and the docs say so. `lastUsedAt` is held in memory and flushed at most every 5 minutes, so a crash can lose recent usage data but never a revocation. The file lands in P4.3 (session epochs), P7.1 (PATs and grants) and P7.7 (push).

### S.7 Session and login hardening

**Decision.** The session cookie is `__Host-dash_session` when the public URL is https. Its payload carries no role; the role is re-derived on every request from the current mapping, so a mapping change applies on the next request instead of after 12 hours. Each user has a session epoch, bumped by "log out everywhere" (which also revokes the user's OAuth grants) and by a password change; the global epoch remains. After 5 login failures per peer or per user the delay doubles from 1 s up to 15 minutes, with a generic error. Passwords use argon2id t=3, m=64 MiB, p=4 (RFC 9106) with at most 2 concurrent hashes. The setup token is `dash_setup_…`, `/setup` returns 404 once an admin exists, and the logs API redacts every secret shape including `dash_setup_`. `anonymousViewer` never gets logs. (Design M.8, M.9.) Proposed with the design; accepted.

**Alternatives considered.**
- Seal the role in the cookie for 12 hours: a demoted admin keeps admin until expiry.
- Only the global epoch: signing out one user would log out everybody.
- Server-side sessions: needs a session store, against ADR 0001 decision 3. Sessions stay stateless signed cookies.
- Lighter argon2id parameters: faster logins, but weaker against offline cracking. The concurrency cap keeps a login flood from exhausting memory.

**Consequences.** Role changes need no forced logout. Login throttling means a locked-out user waits; a legitimate user behind a shared proxy peer can be slowed by an attacker, which is accepted. The cookie rename logs everyone out once at upgrade. Delivered in P4.3.

### S.8 MCP server inside dash

**Decision. Decided by the owner on 2026-10-31.** dash serves MCP at `POST /mcp`: Streamable HTTP, stateless, protocol `2026-07-28`, through the official Go SDK (`github.com/modelcontextprotocol/go-sdk` v1.8.0 or later). It is `mcp.enabled: false` by default; disabled means `/mcp` and its metadata return 404. It is unavailable in `auth.mode: none`. Tokens must have audience `mcp`. A present `Origin` header must match the public URL origin or `server.corsOrigins`. Serving `2025-11-25` as well, and the SDK's localhost-protection opt-out, are unverified and are confirmed in P7.3; the fallbacks in the design apply if the SDK cannot do them. (Design N.1.)

**Alternatives considered.**
- A separate MCP sidecar process: another image, another credential and another place to forward every permission check. Putting it in dash reuses the principal, scope, audit and rate-limit code.
- Stdio-only MCP: cannot serve remote agents or claude.ai-style clients and has no per-user authentication.
- Stateful sessions: conflict with the stateless 2026-07-28 transport and with running more than one replica read-only.
- A hand-written MCP implementation: avoidable protocol and security surface when the official SDK exists.

**Consequences.** dash gains a dependency and a second authenticated surface with its own audience. The off-by-default switch means existing deployments are unaffected. The SDK's protocol support limits what dash can promise until P7.3 checks it. Delivered in P7.3.

### S.9 MCP tools, objects and limits

**Decision.** MCP exposes core read tools (`dash_overview`, `dash_search`, `dash_get`, `dash_context`, `dash_topic`, `dash_series`, `dash_logs`, `dash_approval`), resources for readable topics, four prompts, and one action tool per enabled plugin action, with `inputSchema` from `ActionSpec.Input` and annotations from `Destructive` and `Idempotent`. `tools/list` shows only what the principal can call. A new optional plugin interface `Objects` (`Search`, `Get`, `Context`) backs search and context bundles. No free-form PromQL or LogsQL: series are named and logs are a fixed query shape. Free text from the lab (logs, events, annotations, silence comments, object names) sits in structured fields and, in text output, in a fenced block under a fixed untrusted-data notice. No tool returns Secret or ConfigMap data, and secret redaction applies to all output. Limits are per token: 120 calls per minute, 30 log calls, 10 action calls, 8 concurrent calls, 2 listen streams, 64 KiB per result. Every call is audited, with intent and outcome records for actions. (Design N.2 to N.7.) Proposed with the design; accepted.

**Alternatives considered.**
- Free-form query tools (PromQL, LogsQL, raw Kubernetes `get`): rejected for v1 (S.17). They break the named-series property and are a DoS and exfiltration path.
- A generic Kubernetes passthrough tool: bypasses plugin policy, namespace denial and audit.
- Returning raw logs and events without framing: workload logs are attacker-influenced text, so prompt injection is expected. Framing and structure reduce it; approvals (S.10) contain what remains.

**Consequences.** Seven plugins implement `Objects` (P7.3); a plugin without it is invisible to search. The framing mitigates prompt injection but does not eliminate it, which is why writes need approval. The tool and prompt set becomes a compatibility surface once MCP clients rely on it. The log tool needs the `logs` scope and honours the log namespace policy.

### S.10 Agent actions need human approval

**Decision. Decided by the owner on 2026-10-31.** `plugins.<id>.actions.agents` is `deny`, `approve` or `allow`, default `approve`, and applies only to `mcp`-audience principals. With `approve`, an agent's action call creates an approval request owned by the requesting user, valid for 10 minutes, and notifies them (user-scoped `core.approvals` topic and Web Push). The same user decides in the SPA at `/approve/<id>`, with the client, action, target, summary and full input visible; protected targets need the typed name. dash executes the action server-side on approval, as the requester, and records who approved. Duplicates are deduplicated and each user has at most 20 pending requests. Approvals live in memory, so a restart expires them. A notification tap only opens the page; there are no inline approve buttons. The `approvals` scope is never available to an agent client (S.3). (Design O.)

**Alternatives considered.**
- Agent writes allowed by default: one prompt-injected log line could then restart or delete workloads without a human seeing it.
- Agents blocked from all writes: safe but removes the point of managing the infrastructure through an agent. `deny` remains available per plugin and `allow` is an explicit opt-in.
- The agent executes after a confirmation exchanged with its own client: the confirmation would be controlled by the party being restrained. dash itself runs the approved action.
- Step-up re-authentication for approvals: rejected for v1 (S.17); a hijacked session could approve anyway.
- Persist approvals across restarts: a restart is a rare event and a stale approval is more dangerous than an expired one.

**Consequences.** An agent action takes human time and an agent must handle `pending_approval` (or an MCP multi-round-trip result when the client supports URL elicitation). A user who is away leaves requests to expire. Static tokens cannot own approvals and cannot hold `actions:*` on the `mcp` audience. API-audience tokens and interactive principals follow roles, scopes and UI confirmations, not approvals. Delivered in P7.5.

### S.11 PWA first, one Web Push sender, no FCM relay

**Decision. Decided by the owner on 2026-10-31.** The first mobile client is an installable PWA: a manifest and a hand-written service worker that precaches the app shell, never caches `/api`, `/oauth` or `/mcp`, and handles `push` and `notificationclick`. `internal/push` implements RFC 8030, RFC 8291 (`aes128gcm` only) and RFC 8292 VAPID (ES256). The same sender serves browsers and UnifiedPush distributors such as ntfy. New subscriptions are verified with a code before they receive anything; endpoints must be https and resolve to global addresses unless allow-listed in `push.allowPrivate`; delivery is rate-limited. Approvals are always pushed; attention items are pushed once they persist for 2 minutes, with hourly caps. Push needs `DASH_SECRET_KEY` and a writable data dir. No project-run relay and no FCM in v1. (Design P.1 to P.3.)

**Alternatives considered.**
- A native app only: a PWA delivers phone access now, on iOS and Android, without app stores.
- FCM through a project-run relay: needs infrastructure the project would host and a phone-home path, which is a non-goal (S.17).
- Workbox: another dependency for a service worker that is small and must stay auditable.
- Unverified subscriptions: a subscription endpoint is an outbound URL chosen by the caller, so unverified delivery would be a server-side request forgery and spam primitive.

**Consequences.** iOS delivers Web Push only to apps added to the home screen. Operators on a LAN-only ntfy must allow its address explicitly. Push payloads carry no secrets and open a page for the real content. The push stack has security surface of its own (outbound URL handling, encryption); it is covered by RFC test vectors. Delivered in P7.6 and P7.7.

### S.12 Native Android app in a separate repository

**Decision. Decided by the owner on 2026-10-31.** The Android app lives in its own repository and builds against a contract: server URL typed or scanned from a QR code that carries the URL only; sign-in with AppAuth-Android, Custom Tabs and PKCE (RFC 8252), using the `dash-android` client with `resource=<publicURL>/api` and scopes `read logs approvals push` (optionally `actions:*`); data from `/api/v1`; live updates over `/api/v1/stream?topics=` with an `Authorization` header; background updates only through push, using a UnifiedPush connector registered as `kind: unifiedpush`. No FCM in v1. The redirect scheme for the first-party client is `io.github.techdufus.dash:/oauth2redirect`. (Design P.4.)

**Alternatives considered.**
- The app in this repository: mixes an Android toolchain and release cadence with a Go and Vite project.
- A WebView wrapper around the SPA: gives up native push and a proper OAuth flow.
- FCM: needs a relay and Google services (S.11, S.17).
- A custom login protocol: AppAuth and RFC 8252 are the standard answer for native apps.

**Consequences.** The server contract (S.1 to S.5) must stay stable for an app that ships separately; breaking it in 0.x needs coordination. The redirect URI and application ID are a published identifier and cannot be changed casually. Phones that cannot run UnifiedPush get no background alerts. Client documentation ships in P7.8.

### S.13 MCP first for AI; the assistant later

**Decision. Decided by the owner on 2026-10-31.** AI integration ships as MCP plus "Copy context for AI" (Markdown to the clipboard with no network) on the pod sheet, VM sheet, overview attention items and alert rows, plus agent documentation and a skill file, all in phase 7. A built-in `assistant` plugin comes later and is off by default: an OpenAI-compatible client with read tools only, limited to the user's read scopes, that can render a "Run action" button opening the normal confirmation but never executes an action. Settings warns when the `baseURL` host is not loopback or private. Answers render as sanitised Markdown with no raw HTML. dash does not run an LLM itself in phase 7. (Design Q.1, Q.2.)

**Alternatives considered.**
- A built-in assistant first: needs a model provider, egress and a data-handling story before the project has an API clients story.
- No AI features: users already point agents at their infrastructure. A governed MCP endpoint with approvals is safer than ad-hoc kubeconfig or shell access.
- An assistant that can run actions: the approval model (S.10) is designed for external agents; a built-in assistant with write access would need its own equivalent.

**Consequences.** Users bring their own agent and model. The assistant plugin (P7.9) is explicitly outside the phase-7 acceptance. Anything sent to a remote model is the operator's choice and is warned about. Context bundles reuse the same redaction and the same untrusted-data framing as MCP.

### S.14 UI-editable settings: amends ADR 0001 decision 4

**Decision.** This amends decision 4 of ADR 0001 on two points.
1. `server.*`, `auth.*`, `settings.ui` and `dataDir` are never UI-editable, whatever the other layers say. A settings write that touches one returns `409 Conflict` with code `locked_field` and `source: "ui-ineligible"`. They come from the file, env or defaults only.
2. Decision 4 said secret references are a value form usable in any layer. In the UI layer only encrypted literals and `k8s:` refs are accepted. `env:` and `file:` refs are accepted only from the file and env layers.

"Test connection" and save never send a stored secret to a URL or host other than the saved one; the form must re-enter it. Plugin HTTP clients refuse to dial link-local addresses always, and loopback addresses when the URL came from the UI layer. (Design A.3, B.2, C.2 amendments; review findings K.22, K.23.) Proposed with the design; accepted.

**Alternatives considered.**
- Keep decision 4 as written: a settings-page admin could point a secret at an arbitrary file or process variable, or point a connection test at an attacker URL, and read secrets back that way. An admin in the UI is not the same trust as an operator who controls the file and env.
- Make `auth.*` UI-editable: an admin could lock themselves out, or widen who is admin, from a browser session that may be stolen.
- Remove `k8s:` refs from the UI layer too: they are bounded by Kubernetes RBAC (`resourceNames`), so they remain safe and useful.

**Consequences.** Authentication and listener settings can be changed only by an operator who can edit the file or env, which suits GitOps. The UI shows these fields read-only with a source. The settings API gains the `ui-ineligible` source and the secret-reference rule, with tests in P4.7. ADR 0001 decision 4 should be read together with this decision.

### S.15 Proxy mode fails closed; trust is the TCP peer

**Decision.** In `proxy` mode, trust is decided by the TCP peer only; `X-Forwarded-For` never decides it. If `adminUsers` and `adminGroups` are both empty, every authenticated user is a **viewer**. `adminUsers: ["*"]` restores everyone-is-admin explicitly, with a startup warning. Bearer requests ignore identity headers entirely (S.2). (Design E.2, E.4 amendments; review finding K.2.) Proposed with the design; accepted.

**Alternatives considered.**
- Keep the previous behaviour of everyone being admin when the lists are empty: a new proxy-mode install would grant admin to anyone the proxy lets through by accident.
- Trust `X-Forwarded-For` to find the real peer: a header any client can set.
- Fail closed to nobody (refuse to start): a viewer default keeps the dashboard usable while denying settings and actions.

**Consequences.** Existing proxy-mode deployments must set an admin list (or `["*"]`) in the release that introduces roles, or they lose admin until they do. Header spoofing from a non-proxy peer is rejected. Delivered in P4.1 and P4.2.

### S.16 Dev only on loopback, demo separate from dev, Host allow-list

**Decision.** `DASH_DEV=true` signs every request in as `dev` without authentication, so dash refuses to start unless `DASH_LISTEN` is a loopback address. `DASH_DEMO` no longer implies dev: it keeps the dev defaults for URLs and ports but never uses the `dev` user. The API answers only allowed Host names: the `DASH_PUBLIC_URL` host, the entries of `DASH_ALLOWED_HOSTS`, and loopback names in dev and demo; others get 421. The health listener is not checked, because probes use IPs. This is implemented by the hardening PR (branch `fix/api-hardening`), not by phase 7. (Design K.1, K.10.) Proposed with the design; accepted.

**Alternatives considered.**
- Leave dev mode on any address: one environment variable on a reachable listener would turn off authentication.
- Let demo imply dev: a public demo would inherit the auth bypass.
- No Host validation: leaves DNS rebinding open against an instance bound to a private address.
- Validate the Host header on the health listener too: probes address the pod IP and would fail.

**Consequences.** A reverse proxy that rewrites the Host header needs `DASH_ALLOWED_HOSTS`, which accepts `*` as an explicit opt-out. The existing homelab deployment keeps the original Host through its proxy, so no environment change is needed there.

### S.17 Rejected for v1

**Decision.** The following are not built in v1:

| Rejected | Reason |
|---|---|
| Free-form PromQL/LogsQL tools | They break the named-series property and are a DoS and exfiltration path. |
| Kubernetes impersonation | Needs `impersonate` RBAC and an identity mapping; roles, scopes, approvals and the admission guardrail are the fence. |
| RFC 8628 device grant | PATs cover headless use; capable phones use RFC 8252. |
| Step-up re-authentication | Approvals cover agent writes; a hijacked session can approve anyway; CSP, SameSite and Origin are the defence. |
| MCP sampling | Deprecated in MCP 2026-07-28. |
| Project-run FCM relay | No project infrastructure and no phone-home. |
| Autonomous remediation and VM power actions | Out of scope; no agent acts without approval (S.10), and VM start/stop stays unbuilt until requested. |

(Design Q.3.) Proposed with the design; accepted.

**Alternatives considered.** Each rejected item is its own alternative to the decision it was weighed against (S.4, S.5, S.9, S.10, S.11).

**Consequences.** Each item can return in a later ADR. Users who need headless OAuth use PATs. Users who want Kubernetes-level attribution for agent actions rely on dash's audit trail instead of the cluster's. Telemetry stays out of scope.

## Consequences overall

- The decisions are implemented by phase 7 of the plan (design section R and epic group G7) plus amendments to phases 0 to 6. Phase 7 depends on the plugin API (G2, G3), the auth work (P4.2 to P4.4) and the secrets store (P1.5), and is not required for the public release (P6.10).
- The current-code fixes behind S.16, the stream and request limits, bounded log reads and the chart CSS change are in the hardening PR, not in this ADR's phases.
- S.14 changes a decision in ADR 0001; the two ADRs are read together.
- Four decisions need work in more than one phase: S.5 (P7.2 plus the chart), S.6 (P4.3, P7.1, P7.7), S.10 (P7.5 plus the audit work of P1.8) and S.11 (P7.6 and P7.7).
- No decision here authorises pushing, merging or publishing; those steps keep needing the owner's go-ahead.
